# سامانه مدیریت کمپین پیامکی

یک سامانه مدیریت کمپین‌های پیامکی مبتنی بر **Python، Streamlit و MongoDB** که امکان فیلتر کردن مشتریان بر اساس اطلاعات سفارش، ساخت کمپین پیامکی، ارسال پیامک و پیگیری وضعیت ارسال هر گیرنده را فراهم می‌کند.

این پروژه با هدف ایجاد یک ساختار ساده، قابل توسعه و قابل تست پیاده‌سازی شده است.

---

## امکانات

### مدیریت و فیلتر مشتریان

امکان فیلتر کردن مشتریان بر اساس:

* بازه تاریخ پرداخت سفارش
* محصول
* کد تخفیف
* بازه مبلغ خرید

فیلترها ابتدا روی MongoDB اعمال می‌شوند و سپس اطلاعات دریافت‌شده برای پردازش مشتریان با Pandas پردازش می‌شود.

در رابط کاربری، نام محصول نمایش داده می‌شود اما برای Query به MongoDB از `product_id` استفاده می‌شود.

---

### پردازش مشتریان

ممکن است یک مشتری چندین سفارش داشته باشد.

برای جلوگیری از ایجاد چند گیرنده برای یک مشتری، سفارش‌ها بر اساس شماره تلفن نرمال‌شده گروه‌بندی می‌شوند.

برای هر مشتری اطلاعات زیر محاسبه می‌شود:

* نام
* نام خانوادگی
* تعداد سفارش‌ها
* مجموع مبلغ خرید
* تاریخ آخرین خرید

شماره‌های تلفن نامعتبر از لیست مشتریان حذف می‌شوند و تعداد آن‌ها نیز در رابط کاربری نمایش داده می‌شود.

---

## نرمال‌سازی شماره تلفن

شماره‌های موبایل ایران قبل از استفاده در کمپین نرمال می‌شوند.

فرمت‌های مختلف زیر پشتیبانی می‌شوند:

```text
09123456789
989123456789
00989123456789
۰۹۱۲۳۴۵۶۷۸۹
0912-345-6789
```

تمام شماره‌های معتبر به فرمت استاندارد زیر تبدیل می‌شوند:

```text
09123456789
```

شماره‌های نامعتبر وارد کمپین نمی‌شوند.

---

# مدیریت کمپین‌ها

هر کمپین شامل اطلاعات زیر است:

* نام کمپین
* متن پیامک
* شماره فرستنده
* وضعیت کمپین
* آمار ارسال
* زمان ایجاد
* آخرین زمان ارسال

وضعیت‌های مورد استفاده:

```text
draft
pending
sending
completed
```

کمپین ابتدا به صورت `draft` ایجاد می‌شود و هنگام ارسال وارد فرآیند ارسال می‌شود.

کمپین تنها زمانی `completed` می‌شود که تمام گیرنده‌ها با موفقیت پیامک را دریافت کرده باشند.

---

# منطق ارسال مجدد

یکی از بخش‌های مهم پروژه، مدیریت وضعیت هر گیرنده به صورت مستقل است.

وضعیت گیرنده می‌تواند یکی از موارد زیر باشد:

```text
pending
success
failed
```

هنگام ارسال کمپین:

* گیرنده‌های `pending` ارسال می‌شوند.
* گیرنده‌های `failed` دوباره تلاش می‌شوند.
* گیرنده‌های `success` مجدداً ارسال نمی‌شوند.

بنابراین اگر ارسال یک کمپین به صورت ناقص انجام شود، در تلاش بعدی فقط گیرنده‌های ناموفق دوباره امتحان می‌شوند.

برای هر گیرنده، تاریخچه تمام تلاش‌ها نیز در فیلد `attempts` ذخیره می‌شود.

نمونه:

```json
{
  "phone": "09123456789",
  "status": "failed",
  "attempts": [
    {
      "attempt": 1,
      "status": "failed",
      "error": "Provider error"
    },
    {
      "attempt": 2,
      "status": "success"
    }
  ]
}
```

# اتصال به فراز اس‌ام‌اس

برای ارتباط با سرویس پیامکی، یک کلاس مستقل به نام `FarazSMSProvider` ایجاد شده است.

این جداسازی باعث می‌شود منطق ارسال کمپین مستقیماً به جزئیات API سرویس پیامکی وابسته نباشد.

Provider دارای دو حالت است:

```text
mock
live
```

## حالت Mock

حالت پیش‌فرض پروژه `mock` است.

در این حالت هیچ پیامک واقعی ارسال نمی‌شود و Provider به صورت شبیه‌سازی‌شده نتیجه موفق یا ناموفق برمی‌گرداند.

این حالت برای:

* توسعه
* تست
* بررسی منطق Retry
* جلوگیری از ارسال ناخواسته پیامک واقعی

استفاده می‌شود.

## حالت Live

در حالت `live` درخواست واقعی به API فراز اس‌ام‌اس ارسال می‌شود.

API Key از Environment Variable خوانده می‌شود و داخل کد قرار نگرفته است.


# ایجاد کمپین

برای ایجاد کمپین:

1. فیلترهای مشتریان را مشخص کنید.
2. لیست مشتریان را بررسی کنید.
3. نام کمپین را وارد کنید.
4. متن پیامک را وارد کنید.
5. شماره فرستنده را انتخاب کنید.
6. کمپین را ایجاد کنید.

اعتبارسنجی‌های انجام‌شده:

* نام کمپین نمی‌تواند خالی باشد.
* نام کمپین حداقل ۳ کاراکتر باشد.
* متن پیامک نمی‌تواند خالی باشد.
* متن پیامک حداقل ۱۵ کاراکتر باشد.
* شماره فرستنده نمی‌تواند خالی باشد.

پس از ایجاد کمپین، اطلاعات کمپین و گیرنده‌های آن در MongoDB ذخیره می‌شوند.

---

# ارسال کمپین

در صفحه Campaigns، کمپین‌های فعال نمایش داده می‌شوند.

با ارسال کمپین:

1. کمپین دریافت می‌شود.
2. گیرنده‌های `pending` و `failed` پیدا می‌شوند.
3. پیامک برای هر گیرنده ارسال می‌شود.
4. نتیجه ارسال ذخیره می‌شود.
5. وضعیت گیرنده بروزرسانی می‌شود.
6. آمار کمپین محاسبه می‌شود.
7. وضعیت نهایی کمپین بروزرسانی می‌شود.

گیرنده‌هایی که قبلاً موفق بوده‌اند دوباره پیامک دریافت نمی‌کنند.

---

# گزارش کمپین

برای کمپین‌ها امکان دریافت گزارش CSV وجود دارد.

گزارش شامل اطلاعات کمپین و گیرنده‌ها است، از جمله:

* نام کمپین
* وضعیت کمپین
* متن پیام
* شماره فرستنده
* شماره گیرنده
* وضعیت گیرنده
* شماره تلاش
* وضعیت هر تلاش
* پاسخ Provider
* خطای هر تلاش
* زمان تلاش
* زمان ارسال موفق
* خطای گیرنده
* زمان ایجاد کمپین
* آخرین زمان ارسال کمپین

هر تلاش به صورت یک Row جداگانه در CSV قرار می‌گیرد تا تاریخچه کامل ارسال قابل بررسی باشد.

# تست‌ها

برای تست منطق اصلی پروژه از `pytest` و برای شبیه‌سازی MongoDB از `mongomock` استفاده شده است.

اجرای تمام تست‌ها:

```bash
pytest -v
```

تست‌های پروژه بخش‌های اصلی زیر را پوشش می‌دهند.

### نرمال‌سازی شماره تلفن

موارد زیر تست شده‌اند:

* اعداد فارسی
* پیش‌شماره `98`
* پیش‌شماره `0098`
* فاصله و کاراکترهای اضافی
* شماره نامعتبر
* مقدار خالی
* مقدار `None`

### فیلتر مشتریان

موارد زیر تست شده‌اند:

* فیلتر محصول
* فیلتر کد تخفیف
* ترکیب فیلترها
* بازه مبلغ
* بازه تاریخ

### پردازش مشتریان

تست‌ها بررسی می‌کنند که:

* مشتریان تکراری با هم گروه‌بندی شوند.
* تعداد سفارش‌ها درست محاسبه شود.
* مجموع مبلغ خرید درست محاسبه شود.

### ارسال کمپین

مهم‌ترین تست کمپین بررسی می‌کند که:

> گیرنده‌ای که قبلاً ارسال موفق داشته است، در Retry مجدداً پیامک دریافت نکند.

در این تست هم MongoDB و هم SMS Provider به صورت Mock اجرا می‌شوند و هیچ پیامک واقعی ارسال نمی‌شود.

# تنظیمات Pytest

فایل `pytest.ini` شامل تنظیم زیر است:

```ini

```

این تنظیم باعث می‌شود تست‌ها بتوانند Packageهای پروژه را مستقیماً Import کنند.

مثلاً:

```python
from services import campaign_service
```

# حالت توسعه

برای توسعه و تست بهتر است از حالت Mock استفاده شود:

```env
SMS_MODE=mock
```

در این حالت:

* هیچ پیامک واقعی ارسال نمی‌شود.
* نیازی به API Key واقعی نیست.
* موفق یا ناموفق بودن ارسال شبیه‌سازی می‌شود.
* منطق Retry قابل تست است.
* توسعه پروژه بدون ایجاد هزینه پیامکی امکان‌پذیر است.

برای Production باید حالت `live` و API Key معتبر تنظیم شود.

## چرا گیرنده‌ها در Collection جدا ذخیره شده‌اند؟

گیرنده‌های کمپین مستقیماً داخل Document کمپین ذخیره نشده‌اند و برای هر گیرنده یک Document جداگانه ایجاد شده است.

این طراحی امکان موارد زیر را فراهم می‌کند:

* مدیریت مستقل هر گیرنده
* ذخیره چندین Attempt

## چرا SMS Provider جدا شده است؟

منطق ارتباط با API پیامکی در کلاس `FarazSMSProvider` قرار گرفته است.

این طراحی در آینده امکان اضافه کردن Providerهای دیگر را نیز ساده‌تر می‌کند.
